# Chapter 53 — Host Configuration, DHCP, ARP, and Neighbor Discovery

An interface needs more than an address. It needs a prefix, routes, name-resolution settings, and a way to reach the next hop on its link. These values can be configured statically or learned through several protocols that solve different problems.

The central idea is:

> Configuration tells a host what network to use; neighbor discovery tells it how to reach the next hop on the current link.

## 1. Separate four kinds of state

A working host commonly needs:

1. one or more interface addresses and prefix lengths;
2. routes, including zero or more default routes;
3. resolver configuration such as DNS server addresses and search policy;
4. link-layer mappings for directly reachable next hops.

DHCP can supply several configuration values, but ARP or IPv6 Neighbor Discovery resolves local next hops. DNS resolves names to application-usable addresses. Routing selects which next hop needs local resolution. No single protocol is “the network configuration protocol” for every address family and environment.

Keep source information with each value. An address might be static, DHCP-leased, created through IPv6 stateless autoconfiguration, temporary for privacy, or assigned by a tunnel or container runtime.

## 2. DHCPv4 leases reusable configuration

DHCPv4 lets a client obtain an address lease and configuration options. During initial acquisition, the client may not yet have a usable IPv4 address, so exchanges commonly use broadcast and a relay can carry them across a routed boundary.

A familiar simplified sequence is:

```text
client DHCPDISCOVER → available servers
server DHCPOFFER    → client
client DHCPREQUEST  → selected server and other observers
server DHCPACK      → client
```

The mnemonic “DORA” describes one path, not the whole state machine. Clients can reboot with remembered leases, renew directly, rebind more broadly, decline conflicted addresses, or receive negative acknowledgment. Packet order and broadcast/unicast behavior depend on current state.

A lease has time. The client attempts renewal before expiration and can later rebind if the original server is unavailable. An address that once worked is not proof the current lease or configuration remains valid.

## 3. DHCP options are independent values

DHCP can provide a subnet mask, routers, DNS servers, domain information, lease timers, and many other options. The DHCP server does not have to be the default gateway or DNS server. A relay can connect clients to a centralized server outside the local subnet.

Inspect each option rather than saying “DHCP worked” merely because the host received an address. A lease can contain:

- the wrong prefix, causing bad local-delivery decisions;
- a missing or unreachable default gateway;
- stale DNS servers;
- an unexpected search suffix;
- a duplicate or reserved address;
- a very short or expired lifetime.

DHCP does not authenticate ordinary network access by itself. Untrusted servers can supply harmful routes or resolvers unless network controls and endpoint policy constrain them.

## 4. IPv6 configuration combines several mechanisms

An IPv6 interface ordinarily creates a link-local address and performs Duplicate Address Detection. Router Advertisements (RAs), part of Neighbor Discovery, can announce prefixes, default-router information, lifetimes, and flags that guide further configuration.

With Stateless Address Autoconfiguration (SLAAC), a host forms addresses from advertised prefixes. The interface identifier can be stable, temporary, random-looking, or generated by a platform-specific privacy method; do not assume it embeds the MAC address.

DHCPv6 can assign addresses and prefixes or provide configuration without address assignment. It can operate alongside SLAAC. In ordinary IPv6 architecture, default-router discovery comes from RAs rather than the standard DHCPv6 address-assignment exchange.

This means an IPv6 host can have a global address but no usable default router, or a default router but broken DNS configuration. Inspect addresses, router advertisements or installed routes, resolver state, and lifetimes separately.

## 5. ARP resolves an IPv4 next hop on a local link

After route selection, an IPv4 host knows the next-hop IP address. On Ethernet-like links, ARP maps that local IPv4 address to a link-layer address.

```text
Who has 192.0.2.1? Tell 192.0.2.20.   → local broadcast
192.0.2.1 is at 02:00:5e:10:00:01.   → reply
```

The sender caches the mapping for a limited time. To contact a remote destination, it resolves the gateway's address—not the remote host's MAC. Routers do not forward ordinary ARP requests across subnet boundaries.

An incomplete neighbor entry means resolution is still pending or failed. A stale entry is not automatically broken; operating systems can retain and probe cached state. Interpret the platform's neighbor-state model before deleting anything.

Proxy ARP allows one node to answer for another address and can make hosts communicate despite a topology that would otherwise require routing changes. Its presence should be documented because it can hide incorrect prefix configuration.

## 6. IPv6 Neighbor Discovery does more than ARP

IPv6 Neighbor Discovery uses ICMPv6 messages and multicast. It includes:

- Neighbor Solicitation and Advertisement for link-layer resolution and reachability;
- Router Solicitation and Advertisement for router and prefix information;
- Redirect messages under defined conditions;
- Duplicate Address Detection using Neighbor Solicitation;
- Neighbor Unreachability Detection.

Calling Neighbor Discovery “IPv6 ARP” hides these additional responsibilities. It also encourages harmful filtering: blocking required ICMPv6 can break address configuration, next-hop resolution, and path behavior even when application ports are allowed.

Like ARP, Neighbor Discovery is a local-link control mechanism. A host resolves its on-link destination or selected router, not every remote IPv6 endpoint.

## 7. Duplicate addresses create inconsistent evidence

If two interfaces use the same address on one reachable network, neighbor mappings can oscillate, connections can land on the wrong host, and failures can depend on cache timing. DHCP conflict checks and IPv6 Duplicate Address Detection reduce risk but cannot make unauthorized static configuration impossible.

Evidence can include:

- the same IP mapping to different link addresses over time;
- duplicate-address warnings;
- unsolicited ARP or Neighbor Advertisements;
- connectivity changing when one device disconnects;
- switch or Wi-Fi association records placing the addresses on different ports or clients.

Do not respond by assigning another ad hoc static address. Identify the authoritative allocation system and both claimants.

## 8. Neighbor and configuration protocols are trust boundaries

ARP and basic Neighbor Discovery were not designed as strong peer authentication. A malicious or misconfigured local node can advertise false mappings. Rogue DHCP or RA messages can redirect traffic or supply an attacker-controlled resolver or gateway.

Managed networks can use controls such as DHCP snooping, dynamic ARP inspection, RA Guard, port authentication, segmentation, and endpoint policy. These mechanisms have deployment constraints and can themselves break legitimate protocol behavior when misconfigured.

Applications still need end-to-end authentication such as TLS or SSH host verification. A correct local neighbor mapping proves link delivery, not application identity.

## 9. Observe the current configuration sources

| Question | Linux | macOS | Windows |
| --- | --- | --- | --- |
| Addresses and routes | `ip address`; `ip route`; `ip -6 route` | `ifconfig`; `netstat -rn` | `Get-NetIPConfiguration`; `Get-NetRoute` |
| Neighbor cache | `ip neighbor` | `arp -an`; `ndp -an` | `Get-NetNeighbor` |
| DHCP details | `networkctl status` where applicable; client-specific logs | `ipconfig getpacket interface` | `ipconfig /all` |
| Resolver state | `resolvectl status` where applicable | `scutil --dns` | `Get-DnsClientServerAddress`; `Get-DnsClient` |

Linux configuration systems vary: NetworkManager, systemd-networkd, DHCP clients, container runtimes, and distribution tooling expose different evidence. `resolv.conf` may be generated and may not reveal split DNS or per-link resolver policy.

Commands that release or renew leases, flush neighbors, or disable interfaces change live state. Do not use them as first-line diagnostics, especially over a remote session that depends on the interface.

## 10. Diagnose in dependency order

When a host reports “no network”:

1. Confirm the intended interface and link are available.
2. Inventory addresses, prefixes, origins, and valid lifetimes.
3. Inspect selected routes and default-router state.
4. Identify the next-hop address for the failing destination.
5. Inspect neighbor resolution for that next hop.
6. Verify resolver configuration separately from DNS query results.
7. Correlate DHCP, RA, duplicate-address, and interface logs by time.

A self-assigned IPv4 link-local address can indicate failure to obtain expected configuration, but IPv6 link-local presence is normal. Platform-specific fallback behavior must be interpreted in context.

## Common Misconceptions

- “DHCP assigns only an IP address.” It can distribute many independent configuration options.
- “The DHCP server is the gateway.” They are separate roles and often separate systems.
- “ARP finds the remote server's MAC.” It resolves the selected local next hop.
- “IPv6 uses ARP.” Neighbor Discovery uses ICMPv6 and has broader responsibilities.

## Core Computer Science Concept

Dynamic configuration is **leased distributed state**. The client, server, relay, router, and local caches each hold partial state with lifetimes. Correct diagnosis includes the state owner, version, and expiration rather than assuming one permanent truth.

## Engineering Connections

- Cloud instances often learn configuration from virtual DHCP and router services even when no appliance is visible.
- Container networks create neighbor entries and routes in separate namespaces.
- Rogue local configuration can bypass intended DNS or gateway controls, making endpoint authentication essential.
- Lease and RA lifetimes influence maintenance, failover, and how quickly configuration changes converge.

## From the Field

A laptop receives an IPv4 address and can reach local peers but not external networks. Support repeatedly renews the lease because “DHCP is working.” The lease contains the correct address and prefix but no usable router option. Separating assignment from route configuration directs investigation to the DHCP scope or relay policy instead of the wireless link.

## Engineering Review

### What problem does this solve?

It gives hosts reusable network configuration and maps selected on-link next hops to local delivery addresses.

### Why was it designed this way?

Leases centralize changing configuration, while local neighbor protocols avoid configuring every link-layer mapping manually.

### When should I use it?

Use the model for address acquisition, duplicate addresses, missing gateways, stale local reachability, and resolver-source diagnosis.

### When should I avoid it?

Avoid treating DHCP, ARP, or Neighbor Discovery as authenticated application identity or flushing live state before preserving evidence.

### How does this make me a better engineer?

It separates configuration, routing, neighbor resolution, and naming into testable dependencies.

### How does this reduce waste?

It prevents repeated lease renewals and cache flushes when the failing value belongs to another protocol or owner.

## Handbook Principle #53

> Identify who supplied each configuration value, then resolve only the next hop selected by the current route.

## Practical Observation

On one interface you own, record the origin and lifetime of its addresses, prefix, default routes, DNS servers, and current neighbor entries. Choose one remote destination and identify which local next hop—not remote host—requires a neighbor mapping. Do not renew leases, flush caches, or alter the interface.
